## 1. Google history and the sources behind each ported tip: are the deck's claims fair?

### Takeaway
The history is accurate with small tightening: TotT started in 2006 (first episode April 2006), went public on 21 January 2007, is officially "a weekly one-page publication", and the rename to Tech on the Toilet was announced on 3 December 2024. Every ported tip has a real Google source, but four deck claims compress their source: change-detector tests are about tests that mirror the implementation (not about rewordings), Google's mutation testing deliberately does not report a mutation score, "never change tests" is really "strive for unchanging tests unless requirements change", and "tests have no tests" coexists with Google guidance that test utilities and fakes need their own tests.

**Mutation testing ("give graders a mutation score, seed known-bad answers")**
- (V) Goran Petrovic, "Mutation Testing", Google Testing Blog, Monday 12 April 2021. Definition, verbatim: "mutation testing is a method of evaluating test quality by injecting bugs into the code and seeing whether the tests detect the fault or not. The more injected bugs the tests catch, the better they are." and "If a test fails, we say it kills the mutant, and if no tests fail, we say that the mutant is alive." — [Google Testing Blog](https://testing.googleblog.com/2021/04/mutation-testing.html)
- (V) Same post on the score: the hackathon prototype "did not calculate the Mutation score, the ratio of mutants detected by tests, which is a prominent metric in the research literature and the holy grail of evaluating test quality, but just enumerated live mutants", and Google kept that design: live mutants are surfaced as code-review findings, and "It took an outsider to point out that this was a strange approach: mutation testing was classically run on the whole program and the mutation score calculated and used as guidance." — [Google Testing Blog](https://testing.googleblog.com/2021/04/mutation-testing.html)
- (V) Same post, noise control: unproductive mutants are suppressed via "arid nodes"; "at most one mutant in a line" and 7 per file; "In the beginning, the Not Useful rate was around 80%" and was later lowered "to under 50%". Fault coupling experiment: "A total of 33 million test suites were executed to test hundreds of thousands of mutants, finally to conclude that, in around 70% of cases, a bug was coupled with a mutant." Usage grew from "93 code reviews in Q1 of 2016" to "2,500 users in February 2017, to tens of thousands today". — [Google Testing Blog](https://testing.googleblog.com/2021/04/mutation-testing.html)
- (F) Goran Petrović and Marko Ivanković, "State of Mutation Testing at Google", ICSE-SEIP 2018: diff-based, code-review-time mutation with "arid lines"; "The described system is used by 6,000 engineers in Google", "affecting in total more than 14,000 code authors". — [Google Research](https://research.google/pubs/state-of-mutation-testing-at-google/)
- (V) Goran Petrović, Marko Ivanković, Gordon Fraser, René Just, "Practical Mutation Testing at Scale", arXiv 2102.11378, 22 February 2021 (submitted to IEEE; final venue not shown on arXiv): "Evaluation in a code-review-based setting with more than 24,000 developers on more than 1,000 projects shows that the proposed approach produces orders of magnitude fewer mutants". — [arXiv](https://arxiv.org/abs/2102.11378)
- (V) Same four authors, "Does mutation testing improve testing practices?", ICSE 2021, arXiv 2103.07189, 12 March 2021: "By analyzing a large dataset of almost 15 million mutants ... developers using mutation testing write more tests, and actively improve their test suites with high quality tests such that fewer mutants remain." — [arXiv](https://arxiv.org/abs/2103.07189)

**Change-detector tests ("accept correct rewordings")**
- (V) Alex Eagle, "Testing on the Toilet: Change-Detector Tests Considered Harmful", Google Testing Blog, Tuesday 27 January 2015. The example is a mock-based test that verifies two calls in order. Verbatim: "This is a change-detector test—it is a transformation of the same information in the code under test—and it breaks in response to any change to the production code, without verifying correct behavior of either the original or modified production code." and "Change detectors provide negative value, since the tests do not catch any defects, and the added maintenance cost slows down development. These tests should be re-written or deleted." — [Google Testing Blog](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html)
- (V) The closer Google source for "do not fail a correct answer that is worded differently" is Kai Kent, "Prefer Narrow Assertions in Unit Tests", Google Testing Blog, Thursday 4 April 2024: "Broad assertions are an easy way to accidentally create brittle tests - tests that fail when anything about the system changes, and need frequent fixing even though they aren't finding real bugs." and "the test should use narrow assertions that only check the relevant behavior." — [Google Testing Blog](https://testing.googleblog.com/2024/04/prefer-narrow-assertions-in-unit-tests.html)
- (V) Erik Kuefler (ed. Tom Manshreck), "Unit Testing", chapter 12 of *Software Engineering at Google*: "a brittle test is one that fails in the face of an unrelated change to production code that does not introduce any real bugs." — [SWE at Google ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)

**A/B diff tests ("run A vs A before A vs B, know the noise floor first")**
- (V) Joseph Graves (ed. Tom Manshreck), "Larger Testing", chapter 14 of *Software Engineering at Google*. Verbatim: "A/B diff tests operate by sending traffic to a public API and comparing the responses between old and new versions (especially during migrations). Any deviations in behavior must be reconciled as either anticipated or unanticipated (regressions)." and "We use A-A testing (comparing a system to itself) to identify nondeterministic behavior, noise, and flakiness, and to help remove those from A-B diffs. We also occasionally use A-B-C testing, comparing the last production version, the baseline build, and a pending change". — [SWE at Google ch. 14](https://abseil.io/resources/swe-book/html/ch14.html)
- (V) Same chapter: "A/B diff tests are possibly the most common form of larger testing at Google. This approach conceptually dates back to 1998. At Google, we have been running tests based on this model since 2001 for most of our products, starting with Ads, Search, and Maps." Stated limitations: Approval ("Someone must understand the results enough to know whether any differences are expected. Unlike a typical test, it is not clear whether diffs are a good or bad thing"), Noise ("anything that introduces unanticipated noise into the results leads to more manual investigation ... It becomes necessary to remediate noise, and this is a large source of complexity in building a good diff test"), Coverage and Setup. — [SWE at Google ch. 14](https://abseil.io/resources/swe-book/html/ch14.html)

**Verify state-changing calls ("grade writes, not reads; judge outcomes, not steps")**
- (V) Dillon Bly and Andrew Trenk, "Testing on the Toilet: Only Verify State-Changing Method Calls", Google Testing Blog, Monday 11 December 2017. Verbatim: "State-changing: methods that have side effects and change the world outside the code under test, e.g., sendEmail(), saveRecord(), logAccess(). Non-state-changing: methods that return information about the world outside the code under test and don't modify anything, e.g., getUser(), findResults(), readFile(). You should usually avoid verifying that non-state-changing methods are called". Reasons listed: redundant, brittle, less readable, "false sense of security". Exception: "Verifying non-state-changing method calls may be useful if there is no other output you can assert." The post goes further than the deck: "it would be even better to use a real or fake object to actually execute the method and check that it works properly." — [Google Testing Blog](https://testing.googleblog.com/2017/12/testing-on-toilet-only-verify-state.html)
- (V) Andrew Trenk, "Testing on the Toilet: Testing State vs. Testing Interactions", Google Testing Blog, Friday 22 March 2013: "Testing state means you're verifying that the code under test returns the right results." "Testing interactions means you're verifying that the code under test calls certain methods properly." "Just because a test that uses interactions is passing doesn't mean the code is working properly. This is why in most cases, you want to test state, not interactions." Exceptions: when "differences in the number or order of calls would cause undesired behavior, such as side effects (e.g. you only want one email to be sent), latency ... or multithreading issues". — [Google Testing Blog](https://testing.googleblog.com/2013/03/testing-on-toilet-testing-state-vs.html)
- (V) Andrew Trenk, "Testing on the Toilet: Test Behavior, Not Implementation", Google Testing Blog, Monday 5 August 2013: "In most cases, tests should focus on testing your code's public API, and your code's implementation details shouldn't need to be exposed to tests." — [Google Testing Blog](https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html)
- (V) Andrew Trenk, "Testing on the Toilet: Don't Overuse Mocks", Google Testing Blog, Tuesday 28 May 2013: "not using mocks can sometimes result in tests that are simpler and more useful"; the preferred version asserts on resulting state (`creditCardServer.getMostRecentCharge`). — [Google Testing Blog](https://testing.googleblog.com/2013/05/testing-on-toilet-dont-overuse-mocks.html)
- (V) Andrew Trenk and Dillon Bly, "Test Doubles", chapter 13 of *Software Engineering at Google*: "In general, you should perform interaction testing only for functions that are state-changing." — [SWE at Google ch. 13](https://abseil.io/resources/swe-book/html/ch13.html)

**"Tests have no tests" (deck: graders must)**
- (V) Derek Snyder and Erik Kuefler, "Testing on the Toilet: Tests Too DRY? Make Them DAMP!", Google Testing Blog, Tuesday 3 December 2019. This is the literal source: "Since tests don't have tests, it should be easy for humans to manually inspect them for correctness, even at the expense of greater code duplication." — [Google Testing Blog](https://testing.googleblog.com/2019/12/testing-on-toilet-tests-too-dry-make.html)
- (V) Erik Kuefler, "Unit Testing", SWE at Google ch. 12: "Clear tests are trivially correct upon inspection ... For production code, we're able to write tests that ensure complex logic is correct. But test code doesn't have that luxury—if you feel like you need to write a test to verify your test, something has gone wrong!" — [SWE at Google ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)
- (V) Counter-evidence inside Google's own guidance: Erik Kuefler, "Testing on the Toilet: Don't Put Logic in Tests", Thursday 31 July 2014: "Unlike production code, simplicity is more important than flexibility in tests ... Otherwise it's easy for tests to develop their own bugs." and "Since such helpers can get quite complex, it's usually a good idea for any nontrivial test utility to have its own tests." — [Google Testing Blog](https://testing.googleblog.com/2014/07/testing-on-toilet-dont-put-logic-in.html)
- (V) Andrew Trenk and Dillon Bly, "Increase Test Fidelity By Avoiding Mocks", Google Testing Blog, Tuesday 27 February 2024: a fake "needs its own tests to ensure that it conforms to the behavior of the real implementation". — [Google Testing Blog](https://testing.googleblog.com/2024/02/increase-test-fidelity-by-avoiding-mocks.html)

**"Fix flakiness" (deck: report pass^k)**
- (V) John Micco, "Flaky Tests at Google and How We Mitigate Them", Google Testing Blog, Friday 27 May 2016. Verbatim: "we see a continual rate of about 1.5% of all test runs reporting a 'flaky' result. We define a 'flaky' test result as a test that exhibits both a passing and a failing result with the same code." "We have invested a lot of effort in removing flakiness from tests, but overall the insertion rate is about the same as the fix rate, meaning we are stuck with a certain rate of tests that provide value, but occasionally produce a flaky result. Almost 16% of our tests have some level of flakiness". "about 84% of the transitions we observe from pass to fail involve a flaky test!" Mitigations: re-run failing tests; "a way to denote a test as flaky - causing it to report a failure only if it fails 3 times in a row"; "A tool that monitors the flakiness of tests and if the flakiness is too high, it automatically quarantines the test. Quarantining removes the test from the critical path and files a bug". — [Google Testing Blog](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)
- (V) Jeff Listfield, "Where do our flaky tests come from?", Google Testing Blog, Monday 17 April 2017: "Google has around 4.2 million tests that run on our continuous integration system. Of these, around 63 thousand have a flaky run over the course of a week." "0.5% of our small tests were flaky, 1.6% of our medium tests were flaky, and 14% of our large tests were flaky". "If the root cause is nondeterminism in the production code, ignoring the test means ignoring a production bug." — [Google Testing Blog](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html)
- (V) SWE at Google ch. 11: "Our experience suggests that as you approach 1% flakiness, the tests begin to lose value. At Google, our flaky rate hovers around 0.15%, which implies thousands of flakes every day. We fight hard to keep flakes in check, including actively investing engineering hours to fix them." and "rerunning a test is only delaying the need to address the root cause of flakiness." — [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)
- (V) Source of pass^k: Shunyu Yao, Noah Shinn, Pedram Razavi, Karthik Narasimhan, "τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains", arXiv 2406.12045, 17 June 2024: "we propose a new metric – pass^k (pass hat k), defined as the chance that all k i.i.d. task trials are successful, averaged across tasks." Reported: gpt-4o succeeds "on < 50% of the tasks" and "pass^8 < 25% in retail". — [arXiv](https://arxiv.org/abs/2406.12045)

**"Never change tests" (deck: rotate the items)**
- (V) Erik Kuefler, "Unit Testing", SWE at Google ch. 12, section "Strive for Unchanging Tests": "Any time spent updating old tests is time that can't be spent on more valuable work. Therefore, the ideal test is unchanging: after it's written, it never needs to change unless the requirements of the system under test change." — [SWE at Google ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)
- (F) Same section lists four kinds of change: refactorings and new features should not require changing existing tests; for bug fixes "the bug fix should include that missing test case"; behaviour changes are "the one case when we expect to have to make updates to the system's existing tests." — [SWE at Google ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)

### Inferences
- Deck wording "a weekly one-pager in Google's bathroom stalls", now "Tech on the Toilet": fair and matches Google's own December 2024 description almost word for word. Safer dates to state: started 2006 (first episode April 2006), public since January 2007, rename announced December 2024. The acronym TotT survived the rename.
- The cited 2012 book is a legitimate Google testing reference, but I could not confirm what it says about TotT. The verified sources for TotT history are SWE at Google ch. 11 (book, free online) and the December 2024 blog post; citing one of those next to the name would be stronger.
- Mutation testing port: fair as a port of the general technique, but "mutation score" is the classical metric that Google's own deployment set aside in favour of surfacing individual surviving mutants and suppressing unproductive ones. The more faithful port is "seed realistic known-bad answers, look at which ones the grader lets live, and ignore trivial mutants" (the arid-node lesson: an 80% "not useful" rate before filtering).
- Change-detector port: partly unfair. A change-detector test duplicates the implementation and fails on any change; its closest eval analogue is a grader that checks the exact tool-call sequence or mirrors a reference trajectory. "Accept correct rewordings" is better sourced to "Prefer Narrow Assertions in Unit Tests" (2024) or the brittle-test definition in ch. 12. The slide can keep the tip but should cite both, or re-label.
- A/A before A/B: fully supported, including the phrase "noise" (ch. 14). This is the cleanest port in the deck. The chapter's "Approval" limitation (a human must decide whether a diff is good or bad) also ports and is not in the deck.
- State-changing calls port: fair. Two nuances worth one line: Google's exceptions (verify reads when there is no other observable output; verify interactions when count or order matters for side effects or latency) correspond to legitimate trajectory checks in agent evals (cost budgets, "only one email sent"); and the TotT's stronger advice is to check resulting state with a real or fake dependency rather than verify calls at all, which is exactly what τ-bench does by comparing final database state.
- "Tests have no tests": the literal quote exists (2019 DAMP episode). But Google already tests anything in test code that has logic (helpers, fakes) and uses mutation testing to test tests. So the accurate framing is not that the rule flips, but that an LLM judge is a "nontrivial test utility" and Google's own rule says those get tests.
- "Fix flakiness": fair as Google's stance (ch. 11), though Google itself reports flake rates, auto-retries and quarantines, and concedes it is "stuck with a certain rate". The two Google figures (1.5% of test runs flaky in 2016; a 0.15% flaky rate in the 2020 book) measure different things at different times and should not be combined. A sharper framing: harness and grader noise is still flakiness to fix (A-A testing finds it); model variance is the measurand, so report it (pass^k).
- "Never change tests": overstated. The source says tests should not change unless requirements change, and names behaviour changes as the expected reason to update them. "Strive for unchanging tests" is the quotable form.
- The deck's mapping "CI on every commit" is looser than Google practice: see section 2 (presubmit runs a subset; post-submit runs "all potentially affected tests"), which actually strengthens the port to tiered eval cadences.

## 2. Google testing ideas that port to evals but are absent from the deck

### Takeaway
At least a dozen well-sourced Google ideas port directly and are unused: the test pyramid and its 2024 SMURF refinement, resource-defined test sizes and hermeticity, the Beyoncé Rule, DAMP, coverage as a lossy metric, canarying and probers, quarantine, presubmit versus post-submit selection, fuzzing, testing via public APIs, fidelity over isolation, and rater evaluation. The single most relevant line for the deck is in Google's own book: rater evaluation "is critical for nondeterministic systems like machine learning systems".

### Cited Findings
- **Test pyramid / "Just Say No to More End-to-End Tests"** (V): Mike Wacker, Google Testing Blog, Wednesday 22 April 2015. "As a good first guess, Google often suggests a 70/20/10 split: 70% unit tests, 20% integration tests, and 10% end-to-end tests." Anti-patterns named: "Inverted pyramid/ice cream cone" and "Hourglass". Also: "A failing test does not directly benefit the user." and the ideal feedback loop is fast, reliable and isolates failures. — [Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)
- (V) SWE at Google ch. 11 gives a different ratio: "around 80% of our tests being narrow-scoped unit tests ... 15% medium-scoped integration tests ... and 5% end-to-end tests". — [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)
- **SMURF** (V): Adam Bender, "SMURF: Beyond the Test Pyramid", Google Testing Blog (TotT episode), Tuesday 15 October 2024. "The test pyramid is the canonical heuristic for guiding test suite evolution ... While useful, the test pyramid lacks the details you need". Mnemonic: Speed, Maintainability, Utilization, Reliability, Fidelity; "Reliable tests only fail when an actual problem has been discovered"; "High-fidelity tests come closer to approximating real operating conditions". — [Google Testing Blog](https://testing.googleblog.com/2024/10/smurf-beyond-test-pyramid.html)
- **Test sizes** (V): Simon Stewart, "Test Sizes", Google Testing Blog, Monday 13 December 2010. Small / Medium / Large are defined by resources, not names: network access (No / localhost only / Yes), database, file system, external systems, and time limits of 60 / 300 / 900+ seconds. "A Small test equates neatly to a unit test, a Large test to an end-to-end or system test and a Medium test to ... an integration test"; tests must run in any order. — [Google Testing Blog](https://testing.googleblog.com/2010/12/test-sizes.html)
- **Hermetic tests** (V): SWE at Google ch. 11: "All tests should strive to be hermetic: a test should contain all of the information necessary to set up, execute, and tear down its environment." Ch. 23 (Rachel Tannenbaum, ed. Lisa Carey): "Hermetic tests: tests run against a test environment (i.e., application servers and resources) that is entirely self-contained (i.e., no external dependencies like production backends)." — [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html); [SWE at Google ch. 23](https://abseil.io/resources/swe-book/html/ch23.html)
- (V) Chaitali Narla and Diego Salas, "Hermetic Servers", Google Testing Blog, Wednesday 3 October 2012: a hermetic server is a "server in a box"; "accessing external servers might lead to flakiness due to lack of determinism or unavailability". — [Google Testing Blog](https://testing.googleblog.com/2012/10/hermetic-servers.html)
- **Beyoncé Rule** (V): SWE at Google ch. 11: "we call it the Beyoncé Rule. Succinctly, it can be stated as follows: 'If you liked it, then you shoulda put a test on it.' The Beyoncé Rule is often invoked by infrastructure teams that are responsible for making changes across the entire codebase. If unrelated infrastructure changes pass all of your tests but still break your team's product, you are on the hook for fixing it and adding the additional tests." — [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)
- **DAMP, not DRY** (V): Snyder and Kuefler, 3 December 2019: "In tests we can use the DAMP principle ('Descriptive and Meaningful Phrases'), which emphasizes readability over uniqueness." (F) SWE ch. 12: "DAMP is not a replacement for DRY; it is complementary to it." — [Google Testing Blog](https://testing.googleblog.com/2019/12/testing-on-toilet-tests-too-dry-make.html); [SWE at Google ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)
- **Code coverage** (V): Carlos Arguelles, Marko Ivanković and Adam Bender, "Code Coverage Best Practices", Google Testing Blog, Friday 7 August 2020: coverage is "a lossy and indirect metric that compresses a lot of information into a single number so it should not be your only source of truth"; "A high code coverage percentage does not guarantee high quality in the test coverage"; "a low code coverage number does guarantee that large areas of the product are going completely untested"; "A better technique to assess whether you're adequately exercising the lines your tests cover, and adequately asserting on failures, is mutation testing." — [Google Testing Blog](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html)
- (V) SWE at Google ch. 11 on the metric becoming a target: "instead of treating 80% like a floor, engineers treat it like a ceiling." — [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)
- **Canarying, probers, release qualification** (V): SWE ch. 14: "Probers are functional tests that run encoded assertions against the production environment"; "Canary analysis is similar, except that it focuses on when a release is being pushed to the production environment ... compare health metrics of both the canary and baseline parts of production". SWE ch. 23: "As CD builds RCs, it will run larger tests against the entire candidate"; "We should run the same suite of tests against production (sometimes called probers) that we did against the release candidate". — [SWE at Google ch. 14](https://abseil.io/resources/swe-book/html/ch14.html); [SWE at Google ch. 23](https://abseil.io/resources/swe-book/html/ch23.html)
- (F) Alec Warner and Štěpán Davidovič et al., "Canarying Releases", chapter 16 of *The Site Reliability Workbook*: "We define canarying as a partial and time-limited deployment of a change in a service and its evaluation."; "Canarying is effectively an A/B testing process."; section heading "Before/After Evaluation Is Risky". — [Google SRE Workbook](https://sre.google/workbook/canarying-releases/)
- (V) SWE ch. 24 (Radha Narayan, Bobbi Jones, Sheri Shipe, David Owens): "Automated A/B releases allow for statistically significant results proving a release's quality, without tired humans needing to look at dashboards and make decisions." — [SWE at Google ch. 24](https://abseil.io/resources/swe-book/html/ch24.html)

### Inferences
- Suggested ports, in order of how cleanly they transfer: (1) Beyoncé Rule: a model upgrade is the "unrelated infrastructure change"; if a behaviour matters and has no eval, the model swap is allowed to break it. (2) Test sizes and hermeticity: classify evals by what they are allowed to touch (no tools, sandboxed tools, live web) and by time budget; Listfield's 0.5% / 1.6% / 14% flakiness by size predicts that large agentic evals will be the noisy ones. (3) SMURF: pick the eval mix by speed, maintenance, cost, reliability and fidelity instead of by pyramid dogma, which matters because the pyramid's shape is contested for LLM systems (section 5). (4) Presubmit versus post-submit: cheap code-graded evals on every change, expensive judged or agentic suites asynchronously; this is a more accurate rendering of Google CI than "CI on every commit". (5) Quarantine: move noisy items or graders off the gating path and file a bug, rather than deleting or ignoring them. (6) Coverage: track which capabilities or failure modes the eval set exercises, and expect any score threshold to become a ceiling. (7) Canary and probers: online evaluation on sampled production traffic and scheduled smoke evals; "before/after evaluation is risky" argues for concurrent A/B over sequential comparisons. (8) Public API and fidelity: evaluate the whole deployed system (prompt, tools, harness), not the bare model, and prefer real tools or fakes over mocked tool outputs. (9) Fuzzing: generated and adversarial inputs, red teaming. (10) DAMP: each case and rubric should be readable on its own. (11) Rater evaluation and the A/B diff "Approval" step: Google's own book routes non-deterministic ML outputs to human comparative judgement, which supports the deck's grader-validation theme. (12) "Working as implemented": the person who wrote the prompt should not be the only author of its evals.
- The 2026 "non-default values" episode ports as: choose cases whose correct answer is not what the model would say by default, so a model that did no work cannot pass.

### Gaps
- No Google source was found (or looked for in depth) that itself applies these testing rules to LLM evaluation; the ports above are my inferences.
- John Micco's 2017 conference slides on continuous integration at Google were not retrieved.
- The first appearance of the Beyoncé Rule outside ch. 11 (it is also discussed elsewhere in the book) was not traced.

## 3. Prior art that ported software testing to ML and LLM evaluation

### Takeaway
The analogy has a continuous lineage from 2017: Google's ML Test Score (a rubric explicitly modelled on Google's Test Certified programme), coverage, mutation and metamorphic testing for deep networks (2017-2018), CheckList (ACL 2020, unit-test and metamorphic-test inspired), then for LLM pipelines assertions (SPADE), validator alignment (EvalGen), simulated-user agent benchmarks with pass^k (τ-bench), and perturbation tests of LLM judges. Almost every deck idea has a published precedent; the deck's contribution is the Google-rule framing, not the underlying moves.

### Cited Findings
- (V) Eric Breck, Shanqing Cai, Eric Nielsen, Michael Salib, D. Sculley (Google), "The ML Test Score: A Rubric for ML Production Readiness and Technical Debt Reduction", IEEE Big Data 2017. "we present 28 specific tests and monitoring needs"; "it can be difficult to formulate specific tests, given that the actual prediction behavior of any given model is difficult to specify a priori." Four sections: "Tests for Features and Data", "Tests for Model Development", "Tests for ML Infrastructure", "Monitoring Tests for ML". Individual items already use software-testing vocabulary: "Infra 2: Model specification code is unit tested", "Infra 3: The full ML pipeline is integration tested", "Infra 6: Models are tested via a canary process before they enter production serving environments", "Model 6: Model quality is sufficient on all important data slices", "Monitor 7: The model has not experienced a regression in prediction quality on served data". Scoring: "half a point is awarded for executing the test manually ... A full point is awarded if there is a system in place to run that test automatically on a repeated basis ... The final ML Test Score is computed by taking the minimum of the scores aggregated for each of the 4 sections." ### Inferences
- Deck item to precedent map: "seed known-bad answers" ↔ DeepMutation (2018), Doddapaneni et al. (2024); "graders must have tests" ↔ Shankar et al. "Who Validates the Validators?" (2024) and Anthropic's calibration advice; "accept correct rewordings" ↔ CheckList INV tests and LLM metamorphic testing; "A vs A first" ↔ Madaan et al. and Miller (2024); "grade writes, not reads" ↔ τ-bench's database-state grading and its write / non-write tool split; "report pass^k" ↔ τ-bench; "rotate the items" ↔ Dynabench (2021), LiveBench (2024); "regression suite → golden set" and "capability eval" ↔ Anthropic (January 2026).
- The deck's mapping "unit test → capability eval" mixes two axes. In Google's vocabulary unit / integration / end-to-end is a scope or size axis; in Anthropic's, capability versus regression is a purpose axis (hill to climb versus near-100% guard). CheckList's MFT ("inspired by unit tests") is the published precedent for the scope-axis reading.
- Adoption picture: CheckList is the most cited conceptual bridge (best paper, reused in practitioner guides) but its tooling is not the basis of current LLM eval frameworks; ML Test Score remained a rubric; SPADE reports product deployment (LangSmith); τ-bench's pass^k has been adopted in vendor guidance (Anthropic 2026); metamorphic testing of LLMs remains mostly academic (ICST, ICSME, ASE venues).
- Criteria drift is the strongest research-backed reason the test analogy is imperfect: in software the expected value is known before the test is written; for LLM outputs, people discover the criteria by grading.

- Peer-reviewed venues not confirmed from the pages opened: DeepTest (believed ICSE 2018), the Zhang et al. survey (believed IEEE TSE), SPADE (believed VLDB 2024), "Who Validates the Validators?" (believed UIST 2024).

## 4. Pydantic Evals API fact-check as of 17 November 2026

### Takeaway
`Case`, `Dataset`, `Evaluator`, `Dataset.evaluate_sync()` and `EvaluationReport` are all still the correct names and roles, and the official docs themselves publish a "Unit Testing Analogy" table almost identical to the deck's, with two differences: a test function is `Case` + `Evaluator` together, and the pytest-run equivalent is a named concept, the Experiment. What changed in 2026: Pydantic AI V2 (released 23 June 2026) made `Dataset(name=...)` mandatory and several arguments keyword-only, the docs moved to pydantic.dev/docs/ai, and online evaluation, agentic (trajectory) evaluators and report evaluators are now first-class.

### Cited Findings
- **[2026]** (V) Docs location: `https://ai.pydantic.dev/llms.txt` now redirects to `https://pydantic.dev/docs/ai/llms.txt`; all evals pages live under `pydantic.dev/docs/ai/evals/`. — [Pydantic AI docs index](https://pydantic.dev/docs/ai/llms.txt)

## 6. Talks and essays arguing for or against treating evals as tests

### Takeaway
Nobody credible argues evals are exactly tests; the live disagreement is how far the analogy should steer practice. The strongest "for" case is workflow: fast assertions on every change, regression suites, CI gates, ownership "as routine as maintaining unit tests" (Husain 2024, Anthropic 2026, Arize 2026). The strongest "against" case is epistemic: evals are experiments on a stochastic system whose success criteria are discovered by looking at outputs, so test-first thinking, pass-rate bragging and unit-test-heavy pyramids mislead (Shankar and Husain's FAQ, Miller 2024, Hylak 2025, Marble 2025, Pan 2026).

### Cited Findings

**For the analogy (with stated limits)**
- (F) Hamel Husain, "Your AI Product Needs Evals", hamel.dev, 29 March 2024. Three levels: "Level 1: Unit Tests", "Level 2: Human & Model Eval", "Level 3: A/B testing"; "The cost of Level 3 > Level 2 > Level 1", which "dictates the cadence and manner you execute them". "Unit tests for LLMs are assertions."; they should run fast and cheaply so you can run them on every code change; "unlike traditional unit tests, you don't necessarily need a 100% pass rate." Case study: Rechat's assistant Lucy, with "hundreds of these unit tests". — [Hamel Husain](https://hamel.dev/blog/posts/evals/)
- **[2026]** (V) Anthropic, "Demystifying evals for AI agents", 9 January 2026: "For AI product teams, owning and iterating on evaluations should be as routine as maintaining unit tests." Also uses test language against over-specified graders: checking "a sequence of tool calls in the right order" is "too rigid and results in overly brittle tests". And layers evals with other methods: "Like the Swiss Cheese Model from safety engineering, no single evaluation layer catches every issue." — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- (F) Eugene Yan, "An LLM-as-Judge Won't Save The Product—Fixing Your Process Will", eugeneyan.com, 20 April 2025: "Eval-driven development (EDD) helps us build better AI products. - **[2026]** (F) Mikyo King (Arize), July 2026: "we still think it's worth treating evals as tests", while listing non-determinism, cost, latency and ungradable outputs as the differences. — [Arize](https://arize.com/blog/evals-in-ci-write-your-llm-evals-as-tests/)
- (V) CheckList (ACL 2020) is the academic "for" case: MFTs are "inspired by unit tests in software engineering" and the paper argues "many insights from software engineering are yet to be applied to NLP models." — [ACL Anthology](https://aclanthology.org/2020.acl-main.442/)

**Against, or qualifying**
- (F) Ido Pesok (Vercel, v0), "Evals Are Not Unit Tests", AI Engineer World's Fair 2025, 15:22, [YouTube](https://www.youtube.com/watch?v=L8OoYeDI_ls). On test-first: "Q: Should I practice eval-driven development? Generally no. - (F) Middle ground: Shreya Shankar, "In Defense of AI Evals, for Everyone", sh-reya.com, 5 September 2025, defines evals as "the systematic measurement of application quality" and argues "When people say they 'don't do evals,' they are usually lying to themselves." ### Inferences
- Strongest version of "for": the analogy imports habits that demonstrably work in software and that teams otherwise skip: write the case when the bug appears, run cheap checks on every change, keep a regression suite, gate releases in CI, and treat the suite as owned code. Anthropic's capability-to-regression "graduation" gives the analogy a lifecycle.
- Strongest version of "against": a test asserts conformance to a specification known in advance on a deterministic system; an eval estimates a rate on a stochastic system whose specification is discovered by reading outputs. Importing test instincts wholesale therefore causes four specific errors: test-first evaluators for failures nobody has observed, treating 100% pass as the goal, trusting a single run, and treating the grader as ground truth. Add Hylak's and Marble's points that offline suites only cover known issues and cannot show absence of problems, so monitoring and online evaluation are needed.
- The deck already concedes the "against" side structurally (its "rules that flip" section). It would be more robust if it (a) said explicitly that the analogy is about workflow, not epistemics, (b) acknowledged that "eval-driven development" is contested by the best-known eval educators (section 7), and (c) noted the "Evals Are Not Unit Tests" talk, whose actual content supports the deck's mapping of evals to end-to-end behaviour rather than opposing evals.
- Vercel's people appear on both sides in title only: the 2024 post says evals "are like end-to-end tests", and the 2025 talk says they "are not unit tests". These are consistent.

- Transcript-level verification of the Pesok talk was not done; the summary comes from the event's page.
- I did not find a widely cited essay that argues the analogy is actively harmful (as opposed to incomplete); the Raindrop and Marble pieces are the closest.
- The Hamel and Shankar FAQ existed in earlier versions; the page currently shows September 2026 dates and cites Anthropic's 2026 guidance. The original publication date was not verified.
- Recorded conference talks (PyCon, PyData) that argue the analogy explicitly were not found beyond the AI Engineer talk.

## 7. "Eval-driven development": who coined or popularised it, and what they mean

### Takeaway
No single coiner could be identified. The earliest dated uses I verified are Vercel's blog post of 17 October 2024 and the arXiv paper by Xia et al. of 21 November 2024; Chip Huyen's *AI Engineering* (early 2025), Eugene Yan (April 2025), OpenAI's docs, Anthropic (January 2026) and Braintrust (February 2026) popularised it. The term carries two meanings (evals-first as specification, in the TDD sense, versus evals as a continuous development loop), and the first meaning is explicitly rejected by Husain and Shankar.

### Cited Findings
- (F) Malte Ubl, Alice Alexandra Moore, Ido Pesok, "Eval-driven development: Build better AI faster", Vercel blog, 17 October 2024: "we've needed a new approach: eval-driven development."; evals "become the engine of a new development cycle that we like to call the AI-native flywheel."; "traditional testing methods don't work well with AI's unpredictable nature."; three grading types (code-based, human, LLM-based); for v0: "We prioritize refusal and safety evals, maintaining a 100% pass rate." and "Every GitHub pull request that impacts the output pipeline includes eval results." The post does not mention test-driven development. — [Vercel](https://vercel.com/blog/eval-driven-development-build-better-ai-faster)
- (F) Boming Xia, Qinghua Lu, Liming Zhu, Zhenchang Xing, Dehai Zhao, Hao Zhang, arXiv 2411.13768, v1 21 November 2024; current v3 (17 November 2025) is titled "Evaluation-Driven Development and Operations of LLM Agents: A Process Model and Reference Architecture". It proposes to "embed evaluation as a continuous, governing function rather than a terminal checkpoint" and to unify "offline (development-time) and online (runtime) evaluation within a closed feedback loop", contrasting this with "fixed benchmarks and static test suites". — [arXiv](https://arxiv.org/abs/2411.13768)
- (F) Chip Huyen's *AI Engineering* (O'Reilly) uses "evaluation-driven development" in chapter 4, as summarised by Alex Strick van Linschoten, "Notes on 'AI Engineering' (Chip Huyen) chapter 4", 22 January 2025: "A methodology where AI application development begins with explicit evaluation criteria", "similar to how test-driven development starts with test cases." - (F) Eugene Yan, 20 April 2025: "Eval-driven development (EDD) helps us build better AI products. It's similar to test-driven development where we write tests before implementing software that passes those tests." — [Eugene Yan](https://eugeneyan.com/writing/eval-process/)
- (F) OpenAI, "Evaluation best practices": "Adopt eval-driven development: Evaluate early and often. Write scoped tests at every stage." — [OpenAI developer docs](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
- **[2026]** (V) Anthropic, 9 January 2026: "We recommend practicing eval-driven development: build evals to define planned capabilities before agents can fulfill them, then iterate until the agent performs well. - **[2026]** (F) Braintrust Team, "What is eval-driven development: How to ship high-quality agents without guessing", 18 February 2026: "Eval-driven development is a methodology where evaluations serve as the working specification for LLM-powered applications."; "TDD tests return pass or fail based on an exact match. - **[2026]** (V) Dissent: Husain and Shankar FAQ: "Generally no. Eval-driven development (writing evaluators before implementing features) sounds appealing but creates more problems than it solves ... ### Inferences
- Two meanings are in circulation. Meaning A, specification-first (Anthropic, Yan, Huyen as summarised, Braintrust): write the eval that defines the capability before the system can pass it.
